| | Решение |

| ✅ | Формат входов Go не меняется. |

## 2. Почему стволу не нужна сетка

`b5c384h6nbttflrs` — это 5 блоков `bottlenest2transformerropesg` (`NestedBottleneckTransformerBlock`):

```
1×1 conv 384→192 → [RMSNorm → attention (6 голов × 32, learnable RoPE) → SwiGLU FFN 512] → 1×1 conv 192→384 (+ residual)
```

Свёртка 1×1 — это поэлементный линейный слой по токенам, поэтому ствол работает с любой последовательностью токенов. Сетка проникает в модель только в пяти местах. Каждое из них нужно переделать:

| Место | Сейчас | В разреженном варианте |
|---|---|---|
| Стем | свёртка 3×3 по плоскостям (`initial_conv_1x1=False`) | линейная проекция `POINT`, кодировщик `AREA` (§4.1), глобальные признаки |
| RoPE | `(x, y)` выводятся из индекса токена через `nnXLen` | позиции берутся из буфера по токенам (§4.2) |
| «Размер доски» в gpool / value-голове | сумма маски = площадь поля | сумма маски = число токенов, поэтому площадь берём из `x_size · y_size` |
| Нормализации `fson`, `rsnh` | по маске клеток | по маске токенов, код не меняется |
| Кэш графов cuDNN SDPA | один `seqLen = nnXLen·nnYLen` | `S` динамическая, округляется вверх до кратного 64 |

**Приём для CUDA**: последовательность токенов подаётся как «доска» 1×S с маской. Тогда matmul, нормализации, gpool и SDPA с аддитивной маской `[B,S,S]` работают без изменений.

## 3. Токен `POINT` ✅

Одна выставленная точка **вне внутренности** состоявшихся окружений. 11 признаков:

| № | Признак | Значение |
|---|---|---|
| 0 | `owner` | 0 — наша точка, 1 — точка противника (относительно игрока на ходе) |
| 1–2 | `x/40`, `y/40` | абсолютная позиция = расстояния до левого и нижнего края |
| 3–4 | `(W−1−x)/40`, `(H−1−y)/40` | расстояния до правого и верхнего края |
| 5 | `grounded` | бит заземления из движка |
| 6–10 | `moves_ago = 1…5` | one-hot: точка поставлена 1…5 ходов назад (1 — последний ход соперника) |

**История ходов** — правила как в нынешнем `fillRowV7Dots`:
- берутся до 5 последних ходов, пока цвета строго чередуются;
- `NULL_LOC` пропускается; неразумные ходы (углы и т. п. в реальной партии) не отмечаются;
- заземление в истории — глобальный признак 0 (§5);
- если у игрока нет разумных ходов, кроме заземления, история не подаётся;
- если точка, поставленная `k` ходов назад, уже внутри окружения, она не токен, и её отметка пропадает.

- RoPE: позиция `{(x, y)}`, координаты целочисленные, без масштабирования.
- Фильтрация:
  - точки внутри окружений исключаются;
  - точки границы окружения остаются;
  - точки домиков (и точки внутри домиков) остаются.

## 4. Токен `AREA`

Одно состоявшееся окружение. Если старая область оказывается внутри новой, старая исчезает. Остаётся только внешний контур, а его статистика пересчитывается: каждая точка внутри учитывается ровно один раз, по исходному владельцу.

### 4.1. Содержимое: кодировщик множества вершин границы ✅

Контур — это **множество** координат границы. Порядок обхода признаком не является. Вершины не дублируются внутри одной области, но могут повторяться в разных областях.

**Признаки вершины `b = (x, y)`** ✅. Это только функции координат, других свойств у вершины нет. 24 признака:

| Признак | Значение |
|---|---|
| `x/40`, `y/40` | абсолютная позиция = расстояния до левого и нижнего края |
| `(W−1−x)/40`, `(H−1−y)/40` | расстояния до правого и верхнего края |
| `sin(2πx/P)`, `cos(2πx/P)`, `sin(2πy/P)`, `cos(2πy/P)` для `P ∈ {4, 8, 16, 32, 64}` | Фурье-признаки, 20 штук: мелкие детали формы контура после пулинга |

**Кодировщик**:

```
вершины b ∈ B(a)  → MLP_v (2 слоя, 192, SiLU)            → h_b
агрегат           = [ mean_b h_b ‖ max_b h_b ‖ log(1+|B(a)|) ]
токен AREA        = MLP_a( агрегат ‖ скаляры области ) → 384
```

**Скаляры области** ✅ (относительно игрока на ходе, делитель 20). Ровно два числа плюс владелец:

| Признак | Описание |
|---|---|
| `owner` | 0 — наша область, 1 — противника |
| `score_value` | сколько очков область приносит сейчас, со знаком для игрока на ходе |
| `recapture_delta` | на сколько изменится `score_my − score_opp`, если область перезахватит её противник |

Убраны: `captured_my`, `captured_opp`, `boundary_len`, bbox. Геометрию сеть берёт из координат границы.

**Как считается** (без рекурсии: движок уже разрешил все вложенные перезахваты, и состояние доски финальное):

Для области `a` с владельцем `O` и соперником `X` берём состояние доски:
- `inside(a)` — пункты внутри контура, все выключенные;
- `B(a)` — точки границы, это активные точки `O`.

Тогда:

```
n_X = число пунктов в inside(a), где стоит точка X      (очки O за эту область)
n_O = число пунктов в inside(a), где стоит точка O      (выключенные свои)

score_value     = n_X                   (для O; для X — со знаком минус)
recapture_delta = −(n_X + n_O + |B(a)|) (для O; для X — со знаком плюс)
```

Перезахват по правилу 6.4: `O` теряет `n_X` очков, а `X` получает все точки `O` внутри нового контура, то есть `n_O` и границу `B(a)`. Это перезахват **минимальным** контуром, вокруг ровно этой области. Если контур соперника захватит ещё что-то рядом, прибавится сверх этого; это свойство конкретного хода, а не области.

**Проверка в тестах.** В стресс-тесте случайных партий для каждого хода, который перезахватывает ровно одну существующую область минимальным контуром, сравниваем `black/white_captures_diff` созданной базы с предсказанным `recapture_delta`.

**Заземлённость области** ✅ отдельно не кодируется. Токен области несёт только координаты границы. Что область образована конкретными точками и что она заземлена, если заземлены её точки (8.4), сеть выучивает сама по токенам `POINT` (у них есть бит `grounded`).

**Реализация**:
- CUDA:
  - `MLP_v` — один matmul по плоскому списку вершин батча;
  - пулинг — новое ядро segment-reduce по смещениям `[start, end)`;
  - `MLP_a` — matmul.
- PyTorch: `scatter_reduce` (`mean`, `amax`).
- Симметрии доски — это преобразование координат вершин. Ни сортировок, ни перестановок слотов.

### 4.2. RoPE для `AREA`: усреднение по границе ✅

**Общая формулировка.** Каждый токен `t` имеет **множество позиций** `P(t)`:
- у `POINT` это одна позиция `{(x, y)}`;
- у `AREA` это вершины её границы `B(a)`.

Для каждой пары измерений RoPE с обучаемой 2D-частотой `ω = (ωx, ωy)`:

```
cos_t = mean_{p ∈ P(t)} cos(ω·p)
sin_t = mean_{p ∈ P(t)} sin(ω·p)
```

Дальше применяется обычный поворот `[x0·cos − x1·sin, x0·sin + x1·cos]`. Для `POINT` это в точности стандартный RoPE.

**Смысл.** В комплексной записи поворот на позицию `p` — это умножение на `e^{iω·p}`. Он линеен, поэтому для точки `q` на позиции `p` и области `a` с ключом `k`:

```
score(q@p, k@a) = mean_{b ∈ B(a)} score(q@p, k@b)
```

Логит внимания к области ровно равен **среднему логиту так, как если бы содержимое области стояло в каждой точке её границы**. То же верно для запросов от области и для пар «область–область». Отсюда свойства:
- **Нет фиктивного центра.** Используются только реальные координаты границы.
- **Масштабы разделяются сами.** На низких частотах |среднее| ≈ 1, и область ведёт себя как объект «где-то здесь». На высоких частотах фазы вершин гасят друг друга, и область становится почти безпозиционной. Протяжённая область автоматически «размыта», компактная — «чёткая».
- **Нет дополнительных параметров.** Обучаемые частоты общие для всех токенов.

**Стоимость.** Частоты обучаемые и свои в каждом слое и каждой KV-голове, поэтому таблицы для `AREA` пересчитываются на каждом слое: segment-mean по вершинам от `cos/sin(ω·b)`. Вычислений мало: E вершин × 6 KV-голов × 16 пар × 5 слоёв. В CUDA это одно общее ядро «таблицы cos/sin по множествам позиций», единое для `POINT` и `AREA`. В PyTorch `compute_learnable_rope_cos_sin` уже принимает таблицы формы `(B, S, H, P)`.

**Режим задаётся конфигом модели** ✅: `area_rope = "mean"` (по умолчанию) или `"none"` (NoPE: позиционная часть q/k у `AREA` обнуляется, область общается только содержимым). Оба режима реализуются, сравниваются обучением.

**Свойства:**
- **Нет взрыва значений.** Средние cos/sin лежат в `[−1, 1]`, длина средней «стрелки» ≤ 1. Нормы q/k могут только уменьшиться, поэтому в FP16 безопасно.
- **NoPE содержится как частный случай.** Обучаемая частота `ω → 0` даёт пару, которая не вращается ни у кого. Через такие пары сеть сама может завести каналы «только по содержимому».
- **Большие области.** RoPE даёт только грубое «где-то там», как и для точек. Точные границы сеть берёт из содержимого — закодированных координат вершин. Поэтому размытие крупной области на высоких частотах не проблема, а ожидаемое поведение.

## 6. Policy и выходные головы ❓ (Пакет 2)

### 6.1. Самоубийство и домики ✅

- **По умолчанию самоубийство запрещено.** Сейчас `Rules::DEFAULT_DOTS` создаётся с `multiStoneSuicideLegal = true`; это нужно поменять.
- При запрете самоубийства пункты внутри **чужих** домиков исключаются из действий сети. Пункты внутри **своих** домиков остаются: ходить к себе в домик можно. Движок это уже умеет: `isSuicideDots` — пустой пункт с `getEmptyTerritoryColor == opp`.
- Исключение 5.16 (ход в чужой домик, который сам замыкает своё окружение) остаётся разрешённым: `wouldBeCaptureDots`.
- Официальные правила (5.14) такой ход разрешают. Значит, соперник-человек может его сделать, и вход сети должен корректно обрабатывать чужую точку внутри нашего домика: это обычный `POINT` до следующего хода.

### 6.2. Остальное

Направление: кандидаты ходов не являются токенами ствола. Это **запросы**, которые через cross-attention читают закодированную позицию. RoPE у запроса — позиция пункта, механизм тот же, что в §4.2.

Из правил: ничья — штатный исход (8.6), поэтому value-голова должна быть WDL.

Не решено:
- состав признаков кандидата (тактика захватов, домики);
- источник кандидатов (`getReasonableMoves`);
- заземление как отдельный запрос;
- ownership;
- value / score / td / short-term error;
- policy соперника.

## 7. Формат обучающих данных ❓

Черновик:
- `POINT`: `[N, L_pts, C_pt]` + координаты + счётчики;
- `AREA`: `[N, L_areas, C_area]` + смещения `[start, end)` в плоском списке вершин `[N, E, 2]`;
- глобальные признаки: `[N, C_g]`.

Детали — после фиксации признаков.
