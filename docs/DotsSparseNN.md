# Нейросеть для Точек: разреженная модель

Документ описывает нейросеть для Точек в том виде, в каком она реализована: вход, архитектуру, головы, формат обучающих данных, файл модели, вычисление в C++, а также инструменты проверки.

- Версия модели — **18**, версия входов — **8**. Плотные модели Точек (версии до 17) движок не загружает.
- Правила игры и их отражение в движке: [DotsRules.md](DotsRules.md).
- Целевая модель: **`b5c384h6nbttflrs-fson-silu-rsnh`**.
- Бэкенды: **CUDA** (основной; проверялся на RTX 5060 Ti, sm_120) и **Eigen** (CPU-эталон). Остальные бэкенды модели версии 18 отклоняют с ошибкой.
- Обучение — PyTorch (`python/train.py -games DOTS`). Формат входов Go не менялся.

---

## 1. Ключевые решения

| Решение | Подробности |
|---|---|
| Позиция — это последовательность токенов `[GLOBAL][POINT×P]` | `POINT` — выставленная точка вне внутренностей окружений, `GLOBAL` — один токен позиции. Пустые пункты и состоявшиеся окружения (области) токенами **не являются**: факты области записаны в признаки точек её границы (§4). |
| Ствол KataGo сохраняется | Меняется только входной стем: свёртка по плоскостям заменена эмбеддингом токенов. |
| Действия — запросы декодера | Каждый разумный ход и заземление — кандидат, который через cross-attention читает позицию (§6). |
| Движок пишет только факты | Целочисленные координаты и игровые счётчики; вся геометрия считается в модели одной формулой в PyTorch и C++ (§7.1). |
| Самоубийство запрещено | Модель учится только с этим правилом (§6.1, §10.3). |
| Собственные CUDA-ядра | cuDNN SDPA не используется: длина последовательности меняется от батча к батчу (§10.2). |

## 2. Почему стволу не нужна сетка

`b5c384h6nbttflrs` — это 5 блоков `bottlenest2transformerropesg` (`NestedBottleneckTransformerBlock`):

```
1×1 conv 384→192 → [RMSNorm → attention (6 голов × 32, learnable RoPE) → SwiGLU FFN 512] ×2 → 1×1 conv 192→384 (+ residual)
```

Свёртка 1×1 — это поэлементный линейный слой по токенам, поэтому ствол работает с любой последовательностью. Сетка проникала в плотную модель в четырёх местах, и каждое переделано:

| Место | Плотная модель | Разреженная модель |
|---|---|---|
| Стем | свёртка 3×3 по плоскостям | линейная проекция признаков `POINT` и глобальных признаков |
| RoPE | `(x, y)` выводятся из индекса клетки через `nnXLen` | `(x, y)` берутся из координат точек |
| «Площадь доски» в пулинге и value-голове | сумма маски = площадь поля | сумма маски = число токенов, поэтому площадь берётся из `x_size · y_size` |
| Нормализации `fson`, `rsnh` | по маске клеток | по маске токенов, формулы те же |

## 3. Токен `POINT`

Одна выставленная точка **вне внутренности** состоявшихся окружений. Все признаки — относительно игрока на ходе. 19 признаков:

| № | Признак | Значение |
|---|---|---|
| 0 | `owner` | 0 — точка игрока на ходе, 1 — точка соперника |
| 1–2 | `x/40`, `y/40` | расстояния до левого и нижнего края |
| 3–4 | `(W−1−x)/40`, `(H−1−y)/40` | расстояния до правого и верхнего края |
| 5 | `grounded` | бит заземления из движка |
| 6–10 | `moves_ago = 1…5` | one-hot: точка поставлена 1…5 ходов назад (1 — последний ход соперника) |
| 11 | `area_count` | в границы скольких областей входит точка (0 — ни одной) |
| 12 | `inside_my / 20` | сумма по этим областям: точек игрока на ходе внутри |
| 13 | `inside_opp / 20` | сумма по этим областям: точек соперника внутри |
| 14–18 | `area_moves_ago = 1…5` | one-hot: самая свежая из этих областей появилась 1…5 ходов назад |

Позиция токена для RoPE — `(x, y)`: целые координаты без масштабирования.

**Фильтрация:**
- точки внутри окружений исключаются;
- точки границы окружения остаются;
- точки домиков и точки внутри домиков остаются.

**История не добавляет токенов**: точки последних 5 ходов уже стоят на поле и уже являются токенами. История — это метки в их признаках. Правила те же, что в плотном пути (`fillRowV7Dots`):
- берутся до 5 последних ходов, пока цвета строго чередуются;
- `NULL_LOC` пропускается; неразумные ходы (углы и т. п.) не отмечаются;
- заземление в истории — глобальный признак 0 (§5);
- если у игрока нет разумных ходов, кроме заземления, история не подаётся;
- если точка, поставленная `k` ходов назад, уже внутри окружения, она не токен, и её метка пропадает.

`moves_ago` (6–10) и `area_moves_ago` (14–18) друг друга не дублируют. Первый говорит, когда поставлена сама точка; второй разносит метку хода, создавшего область, на **весь** её контур. Совпадают они только у замыкающей точки.

## 4. Области: факты на граничных точках

Область — одно состоявшееся окружение, только внешний контур. Если старая область оказывается внутри новой, старая исчезает, а каждая точка внутри учитывается ровно один раз, по исходному цвету.

**Отдельного токена у области нет.** Её граница — это выставленные точки владельца вне внутренностей, то есть токены `POINT` с точными координатами, и факты области записаны в них (признаки 11–18 в §3). В признаках только сырые счётчики, никакой арифметики счёта:

| Признак | Описание |
|---|---|
| `area_count` | в границы скольких областей входит точка |
| `inside_my`, `inside_opp` | точек игрока на ходе и соперника внутри этих областей (по цвету постановки), суммы по областям |
| `area_moves_ago` | когда появилась самая свежая из этих областей |

Владелец и заземлённость области отдельно не нужны. Граница — всегда точки владельца (признак `owner`), а заземление распространяется по границе и внутренности как по одной связной группе (бит `grounded` одинаков на всей границе; стресс-тест это проверяет).

**Общая стена.** Точка может входить в границы двух и более своих областей. Тогда счётчики суммируются, `area_count` показывает число областей, а `area_moves_ago` берётся по самой свежей.

**Как считается.** Рекурсии нет: движок уже разрешил все вложенные перезахваты, состояние доски финальное.
- Области — 4-связные компоненты пунктов с `isTerritory` одного активного цвета (владельца).
- Пункты внутри считаются по цвету постановки, пустые не считаются.
- Граница — активные невыключенные точки владельца, 4-смежные с компонентой.

**История области.** Область считается созданной ходом, после которого она появилась на поле в нынешнем виде (нынешний внешний контур). Правила истории те же, что у точек (§3). Без этого признака сеть не видела бы, что последний ход что-то окружил: окружённые точки перестают быть токенами вместе со своими метками.

**Почему этого достаточно.** Для области с владельцем `O` и соперником `X` (`n_O`, `n_X` — их точки внутри, `B` — граница):

```
очки, которые область приносит O     = n_X
изменение для O при её перезахвате X = −(n_X + n_O + |B|)
```

При перезахвате `O` теряет `n_X` очков, а `X` получает выключенные точки `O` внутри и всю границу. Выигрыш конкретного хода движок и так даёт точно — признаки кандидатов `gain_my` / `gain_opp` (§6.2). Форму и длину границы сеть видит по координатам самих точек. Явной группировки «эти точки — одна область» нет: её сеть восстанавливает по соседству точек и одинаковым значениям их признаков.

## 5. Глобальные признаки

| № | Признак | Масштаб |
|---|---|---|
| 0 | заземление в учитываемой истории | 0/1 |
| 1 | коми относительно игрока на ходе | `/20` |
| 2 | заземление сейчас разрешено: `isGroundReasonable` для игрока на ходе или разумных ходов, кроме заземления, нет. Совпадает с наличием кандидата-заземления (§6.2) | 0/1 |
| 3 | `score_my` | `/20` |
| 4 | `score_opp` | `/20` |
| 5 | `score_diff + komi` — фактический перевес игрока на ходе с учётом коми | `/20` |
| 6 | `board_x_size` | `/40` |
| 7 | `board_y_size` | `/40` |

По сравнению с плотной моделью удалены:
- `CaptureEmpty` — нестандартное правило, в обучение такие партии не идут;
- `score_if_i_ground` / `score_if_opp_grounds` — заземление, ведущее к собственному поражению, неразумно и не предлагается; результат заземления несёт его кандидат (§6.2);
- флаг самоубийства — обучение идёт только с запретом самоубийства (§6.1).

## 6. Policy и выходные головы

### 6.1. Самоубийство и домики

- **По умолчанию самоубийство запрещено**: `Rules::DEFAULT_DOTS` создаётся с `multiStoneSuicideLegal = false`, во всех конфигах Точек `suicideLegals = false`.
- Пункты внутри **чужих** домиков исключаются из действий сети. Пункты внутри **своих** домиков остаются: ходить к себе в домик можно.
- Исключение 5.16 (ход в чужой домик, который сам замыкает своё окружение) остаётся разрешённым: `wouldBeCaptureDots`.
- Официальные правила (5.14) ход в чужой домик разрешают, поэтому соперник-человек может его сделать. Чужая точка внутри нашего домика — обычный `POINT` до следующего хода.

### 6.2. Кандидаты действий

Все допустимые действия — **запросы-кандидаты**. Они не являются токенами ствола, а через cross-attention читают закодированную позицию. Между собой кандидаты не общаются. Все M+1 действий получают логиты в **одном общем softmax**.

| Тип | Источник | RoPE |
|---|---|---|
| пункт `(x, y)` | `getReasonableMoves` (см. ниже) | по `(x, y)` |
| заземление | один, если заземление сейчас разрешено; всегда последний | нет (NoPE) |

**Признаки кандидата-пункта** (8):

| Признак | Значение |
|---|---|
| `x/40`, `y/40`, `(W−1−x)/40`, `(H−1−y)/40` | расстояния до краёв, как у `POINT` |
| `gain_my / 20` | на сколько изменится `score_my − score_opp`, если **я** хожу сюда (0, если ход ничего не окружает) |
| `gain_opp / 20` | на сколько изменится `score_opp − score_my`, если сюда пойдёт **соперник** (угроза) |
| `in_my_house` | пункт внутри моего домика |
| `in_opp_house` | пункт внутри домика соперника (при запрете самоубийства — только исключения 5.16) |

**Признак кандидата-заземления** (1): `ground_result / 20` — итоговая `score_my − score_opp + komi`, если я заземляюсь сейчас (партия заканчивается, 8.4).

**Какие пункты становятся кандидатами** (`getReasonableMoves`, `CaptureAndTerritoryInfos::isReasonableMove`):
- ход, который что-то окружает, — всегда;
- не берутся углы и занятые пункты;
- не берутся пункты внутри чужого домика (§6.1);
- не берутся пункты внутри базы, которую **соперник** замыкает одним ходом: точка внутри не мешает замыканию и только добавит ему пленных, а защита — ход в сам замыкающий пункт, и он кандидат;
- не берутся пункты внутри базы, которую **я** замыкаю одним ходом. Из ходов, окружающих одно и то же, движок оставляет дающий наибольшее окружение (`recalculateCapturesAndTerritories` удаляет вложенные базы), а пункты меньших окружений лежат внутри большего.

Пункт, который соперник может окружить следующим ходом, кандидатом остаётся.

### 6.3. Декодер кандидатов

```
ствол (5 блоков) → токены GLOBAL/POINT, 384 канала                ← ключи и значения
кандидат: Linear(свои признаки) + Linear(глобальный пулинг ствола) → 192
× candidate_decoder_layers (по умолчанию 1):
    RMSNorm → cross-attention (6 голов, learnable RoPE; пункт — по (x, y), заземление — NoPE) → SwiGLU FFN
→ RMSNorm → Linear → 6 policy-логитов + 2 futurepos
```

- Кандидат видит **все** токены позиции.
- Кандидаты между собой не общаются, поэтому стоимость линейна по их числу.
- Один слой, как одна policy-голова у KataGo: вся тяжёлая работа — в стволе. Суффикс `-dec2` даёт два слоя («два раунда вопросов») для сравнения обучением.

### 6.4. Выходы кандидатов

Каждый кандидат выдаёт 6 policy-логитов и 2 значения futurepos (§6.6). Softmax каждого policy-выхода считается отдельно по всем M+1 кандидатам.

| № | Выход | Цель обучения | Использование |
|---|---|---|---|
| 0 | policy | распределение посещений поиска | поиск |
| 1 | policy соперника | policy следующей позиции | только обучение |
| 2 | мягкая policy | цель 0 в степени ¼, перенормированная | только обучение |
| 3 | мягкая policy соперника | цель 1 в степени ¼ | только обучение |
| 4 | долгосрочно-оптимистичная | цель 0 с весом партий, сыгранных лучше прогноза | только обучение |
| 5 | краткосрочно-оптимистичная | цель 0 с весом по краткосрочной неожиданности | `policyOptimism` |

Экспортируются только выходы 0 и 5, как у версии 17. Q-значения не используются.

**Policy соперника и наборы кандидатов.** Соперник отвечает в следующей позиции, а кандидаты берутся из текущей.
- Цель выхода 1 — распределение поиска следующей позиции, спроецированное на текущих кандидатов по координате пункта. Заземление соперника проецируется на кандидат-заземление (для выходов 1 и 3 он означает «соперник заземлится»).
- Масса на пунктах, которые сейчас не кандидаты (например, наш ход их выключил), отбрасывается, остаток перенормируется. Если ничего не осталось, пример для выходов 1 и 3 получает вес 0.

### 6.5. Ownership

**Один выход на каждый токен `POINT`**: вероятность, что к концу партии эту точку захватит **соперник её владельца**. Сигмоида, бинарная кросс-энтропия.

Цель — финальное владение из движка (`calculateOwnershipAndWhiteScore`, `finalOwnership` в `trainingwrite.cpp`). Для точки цвета `c`:
- **1**, если `finalOwnership[loc] == opp(c)`:
  - точка в конце стоит внутри области соперника;
  - или при заземлении (8.4) её владелец заземлился, а точка не заземлена;
- **0** во всех остальных случаях:
  - точка активна;
  - точка выключена внутри **своей** области (свои окружённые точки — не захват);
  - точка была захвачена, но освобождена перезахватом.

У точек внутри областей и у пустых пунктов выхода нет. Судьба области всё равно предсказывается: если её перезахватят или она уйдёт сопернику при заземлении, её граничные точки окажутся захвачены, а у них есть выход.

Партии без результата из цели ownership исключаются.

### 6.6. Futurepos

Два дополнительных выхода у каждого кандидата-пункта: `tanh`, по одному на горизонт **+8** и **+32** хода (как у KataGo).

Цель — чья точка будет стоять в этом пункте через 8 (32) ходов:
- **+1** — точка игрока на ходе;
- **−1** — точка соперника;
- **0** — пункт пуст или выключен без точки.

Берётся **цвет постановки** (`getPlacedDotColor`), а не активный цвет: иначе пустые выключенные пункты внутри областей выглядели бы как «камни».

- Если партия кончится раньше, берётся финальная доска.
- У кандидата-заземления futurepos нет: вес 0.
- Потери как у KataGo: квадрат ошибки после `tanh`, веса горизонтов `[1, 0.25]`, нормировка на `sqrt(x_size · y_size)`.

### 6.7. Головы позиции

Все скалярные головы KataGo сохранены и строятся на глобальном пулинге по всем токенам ствола (`GLOBAL` и `POINT`):

| Голова | Что предсказывает |
|---|---|
| value | победа / поражение / нет результата. Ничья (8.6) — цель «победа» = «поражение» = 0.5 (`drawEquivalentWinsForWhite`), отдельного класса нет |
| score mean, score stdev | итоговая разница счёта и её разброс |
| lead | на сколько очков сдвинуть коми до ровной партии |
| variance time | через сколько ходов позиция устаканится |
| td value ×3, td score ×3 | value и счёт на трёх горизонтах |
| short-term value / score error | ошибка краткосрочного прогноза |
| scorebelief | распределение итогового счёта, без члена чётности (у Точек он всегда 0) |

Отличия от KataGo: нет члена чётности, а «площадь доски» в пулинге и нормировках берётся из `x_size · y_size`.

## 7. Формат обучающих данных

### 7.1. Принцип: движок пишет только факты

C++ записывает **целочисленные координаты и игровые факты**: цвета, счётчики, `gain`, биты. Всё, что выводится из координат, модель считает сама из `(x, y)` и размеров поля, одинаковым кодом в PyTorch и C++: `x/40`, расстояния до краёв, RoPE.

Из этого следует:
- **симметрии** при обучении — это только преобразование целочисленных координат (4 для прямоугольного поля, 8 для квадратного), без пересчёта признаков (`apply_symmetry_to_batch`);
- **нет расхождений** между данными и инференсом: геометрию считает одна и та же формула.

### 7.2. Массивы NPZ

Пишутся selfplay (`trainingwrite.cpp`) и `katago writetrainingdata -what-data-source dots` (без метаданных SGF). Хранятся **только факты**, без дополнения и без полос нулей:
- массивы сущностей (точки, кандидаты, кандидаты с ненулевыми целями policy и futurepos) записаны подряд в порядке строк, их число в строке — в счётчиках `…CountN`;
- цели policy и futurepos хранятся только для кандидатов, у которых они ненулевые (в среднем ~4% и ~2.5% кандидатов), с индексом кандидата в строке;
- распределение итогового счёта — его два соседних бина, а не вектор длиной `2·(площадь + 60)`, в котором ненулевых два числа;
- малые значения хранятся в int8.

`ΣP`, `ΣM`, `ΣT`, `ΣF` — суммы `pointCountN`, `candCountN`, `policyTargetCountN`, `futureposTargetCountN` по файлу. Формат читает `python/katago/train/sparse_dots_npz.py`; файлы прежних форматов он переводит в этот при загрузке: и неупакованные с плотными целями кандидатов и полным `scoreDistrN`, и самые первые, дополненные до максимумов файла (`…NP`/`…NM`).

**Входы:**

| Массив | Форма | Тип | Содержимое |
|---|---|---|---|
| `boardSizeN` | `[N, 2]` | int8 | `x_size`, `y_size` |
| `globalInputNC` | `[N, 8]` | float32 | глобальные признаки §5 |
| `pointCountN` | `[N]` | int16 | число точек |
| `pointCoordsP` | `[ΣP, 2]` | int8 | `x`, `y` |
| `pointStateP` | `[ΣP, 5]` | int8 | `owner`, `grounded`, `movesAgo` (0 — нет, 1…5), `areaCount`, `areaMovesAgo` |
| `pointInsideP` | `[ΣP, 2]` | int16 | `insideMy`, `insideOpp` |
| `candCountN` | `[N]` | int16 | число кандидатов-пунктов |
| `candCoordsM` | `[ΣM, 2]` | int8 | `x`, `y` |
| `candGainM` | `[ΣM, 2]` | int16 | `gainMy`, `gainOpp` |
| `candHouseM` | `[ΣM, 2]` | int8 | `inMyHouse`, `inOppHouse` |
| `groundN` | `[N, 2]` | float32 | заземление разрешено (0/1), `ground_result` |

**Цели:**

| Массив | Форма | Тип | Содержимое |
|---|---|---|---|
| `policyTargetCountN` | `[N]` | int16 | число кандидатов с ненулевыми посещениями (мой ход или ответ соперника) |
| `policyTargetCandT` | `[ΣT]` | int16 | индекс такого кандидата в строке |
| `policyTargetsT` | `[ΣT, 2]` | int16 | его посещения: мой ход, ответ соперника (проекция, §6.4) |
| `groundPolicyTargetsN` | `[N, 2]` | int16 | то же для заземления |
| `futureposTargetCountN` | `[N]` | int16 | число кандидатов с ненулевой целью futurepos |
| `futureposTargetCandF` | `[ΣF]` | int16 | индекс такого кандидата в строке |
| `futureposTargetsF` | `[ΣF, 2]` | int8 | +1/−1/0 на горизонтах +8 и +32 |
| `pointOwnershipTargetsP` | `[ΣP]` | int8 | 1 — точку захватит соперник владельца |
| `globalTargetsNC` | `[N, 80]` | float32 | как в плотном формате: value, td, score, веса |

Плотное распределение счёта для потерь собирается из двух бинов на GPU (`metrics_sparse_dots.score_distribution`) под длину выхода модели. Счёт, а не номер бина, делает данные независимыми от размера поля в формате.

Размер на 39×32 (в среднем ≈500 точек и ≈680 кандидатов): ≈11.5 КБ на строку в памяти. Неупакованный формат с плотными целями занимал ≈22 КБ (из них 2.6 КБ — `scoreDistrN`), формат с дополнением до максимумов файла — ≈40 КБ. Файл `train_tf4` (58 тысяч строк): 1.24 ГБ → 0.67 ГБ в памяти, загрузка 4 с → 0.5 с; на диске почти без разницы (нули хорошо сжимались).

### 7.3. Перемешивание и загрузка

`shuffle.py` выбирает и склеивает строки вместе со всеми их сущностями, ничего не дополняя. Загрузчик (`data_processing_sparse_dots.py`) дополняет точки и кандидатов батча до максимума его строк и раскладывает разреженные цели по их кандидатам: батч модели состоит из `pointCoordsNP`, `pointDataNP` (`[B, P, 7]`), `candCoordsNM`, `candDataNM` (`[B, M, 4]`), `candPolicyTargetsNM`, `candFutureposTargetsNM` и массивов строк. Чтобы дополнения было мало, строки группируются по длине: перемешанные строки файла делятся на куски по 32 батча, кусок сортируется по числу точек (число кандидатов почти строго убывает с ним), режется на батчи, и батчи всего файла идут в случайном порядке. В случайных батчах дополнение тратило около половины токенов и около 80% cross-attention. После группировки на токены уходит ≈3%, на cross-attention ≈15%. Если при обучении история частично отключается, метки `movesAgo` и `areaMovesAgo` старше оставленной истории обнуляются.

## 8. Модель и обучение (PyTorch)

Код: `python/katago/train/model_sparse_dots.py` (модель), `metrics_sparse_dots.py` (потери), `data_processing_sparse_dots.py` (загрузчик), `export_model_pytorch.py` (экспорт), `sparse_dots_bin.py` (Python-ридер файла модели).

### 8.1. Выбор конфига

С `-games DOTS` имя трансформерной модели даёт разреженную модель (`modelconfigs.get_config(name, dots=True)`). Суффикс для сравнений: `-dec2` (два слоя декодера вместо одного).

Принимаются только конфиги, которые разреженный путь реализует целиком (`sparse_dots_config_error`). Остальные отклоняются до создания модели с ошибкой, называющей опцию:

| Что | Поддерживается |
|---|---|
| Блоки ствола | `bottlenest2transformerropesg`, `bottlenest3transformerropesg` (FFN в C++ только SwiGLU) |
| Позиции и финальная норма | learnable RoPE, `-rsnh` (spatial RMSNorm), без групп каналов |
| Нормализация | `fixup`, `fixscale`, `fixscaleonenorm` (батч-нормам нужна пространственная раскладка) |
| Активации | `relu`, `mish`, `silu` |
| GQA (`transformer_kv_heads`) | да |
| `qk_norm`, регистры, `dwc`, channel gate, residual backout, RepVGG, `metadata_encoder`, промежуточная голова | нет |

`-attn-logit-penalty-cap` для Точек не поддерживается. Из всех имён в `modelconfigs.py` проверку проходят 117, целевая модель среди них.

### 8.2. Архитектура

- **Последовательность**: `[GLOBAL][POINT×P]`, маска `[N,S,1]`. Токен `GLOBAL` — обучаемый вектор: последовательность никогда не пуста (стартовая позиция без точек даёт 0 токенов `POINT`). Ко всем токенам прибавляется `linear_global(globals)`.
- **Эмбеддинг** `POINT` — `Linear(19→C)` с bias.
- **RoPE**: координаты целые, без масштаба; таблицы cos/sin строятся в каждом слое по его частотам. У `GLOBAL` и кандидата-заземления таблицы нулевые, поэтому их q/k после поворота нулевые (NoPE): такой токен внимает равномерно и сам получает логит 0.
- **Ствол**: штатные `NestedBottleneckTransformerBlock` в раскладке NSC; внимание заменено подклассом `SparseRoPEAttentionBlock` с теми же параметрами, поэтому экспорт и C++-дескрипторы блоков переиспользуются. Финальная норма — spatial RMSNorm по действительным токенам, затем активация.
- **Пулинг для голов**: среднее по действительным токенам, включая `GLOBAL`; смещение `off = sqrt(x_size·y_size) − 14`. Для декодера `[mean, mean·off/10, max]`, для value-головы `[mean, mean·off/10, mean·(off²/100 − 0.1)]`.
- **Декодер**: `Linear(8→Cd)` для пунктов, `Linear(1→Cd)` для заземления, плюс `Linear(3C→Cd)` от пулинга; `Cd` = `mid_num_channels` (192). Слой: `RMSNorm → cross-attention (q из кандидата, k/v из выхода ствола) → SwiGLU FFN`. Затем `RMSNorm → Linear(Cd→8)` без bias. Заземление — кандидат с индексом M, маскированные кандидаты получают −5000.
- **Value-голова**: как у KataGo, но `conv1` → `Linear(C→v1)` + bias; ownership — `Linear(v1→1)` от выхода `act1` на токенах `POINT`.

### 8.3. Потери и обучение

- Веса потерь как у KataGo. Policy — общий softmax по M+1; цель соперника нормируется после проекции, при нулевой сумме вес выходов 1 и 3 равен 0. Ownership — BCE, среднее по точкам строки. Futurepos — по кандидатам-пунктам, `/ sqrt(x_size·y_size)`.
- Модель не зависит от порядка токенов. Геометрически симметричной её делает обучение со случайными симметриями координат, как и свёрточную сеть KataGo.
- `train.py` с `-games DOTS` создаёт разреженную модель, читает разреженные NPZ и считает потери `SparseDotsMetrics`. FP16 (`-use-fp16`) поддерживается: ствол и декодер считаются под autocast, логиты декодера и value-голова — в FP32.
- **`torch.compile`** с динамическими формами (`dynamic=True`): число точек и кандидатов меняется от батча к батчу, а модель и потери компилируются один раз (плюс пара перекомпиляций на порогах размеров). Анализ коалесцирования тайлинга Inductor отключён: на ядрах этой модели он падает (torch 2.11). На Windows Inductor нужен `cl.exe`: если его нет в `PATH`, `train.py` сам берёт окружение Visual Studio (`vswhere` → `vcvars64.bat`), а без него учится без компиляции с предупреждением. Компиляция занимает ~5 минут при первом запуске и ~1–2.5 минуты с прогретым кэшем Inductor, поэтому окупается, когда за запуск `train.py` обучается порядка 50 тысяч строк и больше; для коротких запусков есть `-no-compile`.
- **Загрузка данных** — в процессах-воркерах (`KATAGO_SPARSE_DOTS_DATA_WORKERS`, по умолчанию 2, 0 — в процессе обучения): сборка батча занимает десятки миллисекунд CPU, столько же, сколько шаг, а потоки упирались бы в GIL. Порядок батчей тот же, что и в одном процессе. Скрипты, которые читают данные этим загрузчиком, должны запускать его под `if __name__ == "__main__"` (на Windows воркеры заново импортируют главный модуль).
- **Скорость обучения** (RTX 5060 Ti, FP16, данные `train_tf4` 39×32):

  | Модель, батч | Было (eager, FP32-декодер, сборка в основном потоке) | Стало |
  |---|---|---|
  | b4c256, 128 (`train.py`) | ~410 строк/с | ~880 |
  | b5c384, 64 | ~210–230 | ~490, пик памяти 7.5 → 5.8 ГиБ |
- Цикл selfplay → shuffle → train → export запускается штатным `python/selfplay/synchronous_loop.sh` с видом модели `b5c384h6nbttflrs-fson-silu-rsnh`.

## 9. Файл модели версии 18

Заголовок как у версии 17: имя, `18,maxX,maxY,DOTS,gitRev,backend`, затем `19` (признаки точки), `8` (глобальные), 7 множителей, 8 нулей. Далее:

```
sparse_dots_model
8 1 0 0 0 0 0 0   (признаки кандидата, признаки заземления, 6 запасных)
matmul+matbias linear_point
matbias global_token; matmul linear_global
trunk <num_blocks> <C> <Cmid> <Cmid-Cgpool> <Cgpool> <Cgpool> 1 0 0 0 0 0
  nested_bottleneck_block × num_blocks (как у версии 17)
  rmsnorm norm_trunkfinal; act
model.decoder <Cd> <layers> 0 0
  matmul+matbias linear_cand; matmul+matbias linear_ground; matmul linear_pool
  × layers: transformer_cross_attention_block (формат transformer_attention_block, k/v из C) ; transformer_ffn_block
  transformer rmsnorm norm_final; matmul linear_out (Cd→2: выходы policy 0 и 5)
model.value_head 0 0 0
  matmul linear1; matbias bias1; act; matmul linear2; matbias; act; matmul+matbias valuehead (3);
  matmul+matbias miscvaluehead (6: score mean, stdev, lead, vtime, 2 short-term errors); matmul linear_ownership (v1→1)
```

## 10. Реализация в C++

### 10.1. Извлечение позиции

Код: `cpp/neuralnet/nninputsdotssparse.cpp`, структура `DotsSparseInput` (`nninputs.h`).

- Точки с признаками §3, кандидаты и заземление §6.2, глобальные признаки §5.
- Области (§4) строятся как вспомогательные данные (`DotsSparseInput::areas`): из них агрегируются признаки граничных точек, по ним сверяются тесты. Вход сети они не составляют.
- **`gain_my` / `gain_opp`** считаются ходом с откатом там, где движок вообще пытается окружить (`getColorsOfPotentialCapturing`: не меньше двух несвязанных соседей). `CapturesAndTerritoriesInfos` для этого не подходит: она пропускает окружения ходом внутри собственной потенциальной территории игрока. Ход-самоубийство даёт 0.
- **`ground_result`** = `whiteScoreIfBlackGrounds` (или `blackScoreIfWhiteGrounds`) со стороны игрока на ходе + его коми (тот же коми, что в глобальном признаке 1).
- **Симметрии** применяются только к координатам входа (`DotsSparseInput::withSymmetry`); выходы индексированы кандидатами и точками, обратное преобразование не нужно.
- **Кэш**: хеш NN-входа для Точек включает последние 5 ходов.

### 10.2. Вычисление

- **CPU-эталон** — `cpp/neuralnet/sparsedotsnn.cpp`: одна позиция без дополнения, FP32, те же формулы, что в PyTorch. Им считает бэкенд Eigen, с ним сверяется CUDA. Признаки токенов (`SparseDotsNN::pointFeatures` и др.) общие для эталона и CUDA.
- **CUDA** — `cudasparsedotsmodel.cpp` (модель) и `cudasparsedots.cu` (ядра):
  - **без дополнения (varlen)**: токены ствола и запросы декодера всех позиций батча идут подряд, границы позиций — смещения `tokStart` / `qStart`. Все GEMM и поэлементные ядра работают ровно на Σ(1+P) и Σ(M+1) строк. Дополнение до общего максимума было главным тормозом: в батче из разных партий P и M антикоррелированы (P + M ≈ площадь поля), и строк на позицию выходило почти вдвое больше, чем у плотной модели;
  - признаки собираются на хосте в постоянный pinned-буфер и копируются одним блоком; симметрия применяется к координатам при упаковке, без копирования входа;
  - эмбеддинги, пулинги и value-голова — в FP32; ствол и декодер — в FP16 при `useFP16`, иначе в FP32; GEMM — cuBLAS с накоплением в FP32;
  - q, k и v ствола — одна GEMM, k и v декодера — одна GEMM, `linear1` и `gate` FFN — одна GEMM; RoPE считается на лету в ядре поворота, без таблиц; рабочие буферы ствола и декодера общие;
  - внимание — tensor-core ядро `cudaflashmma.cuh` в режиме varlen (self-attention ствола и cross-attention декодера); при разных размерах голов q и v или в FP32 — скалярное ядро `sparseDotsAttention`;
  - у каждого серверного потока NN свой поток CUDA, поэтому при `numNNServerThreadsPerModel = 2` упаковка одного батча идёт параллельно со счётом другого.
- **ROCm, OpenCL, TensorRT, ONNX, Metal** модели версии 18 не принимают.

### 10.3. Выходы и правила

- Выходы раскладываются в обычный `NNOutput`, поэтому поиск не менялся:
  - логиты кандидатов — в `policyProbs` по их пунктам, заземление — в индекс паса; смешивание с оптимистичной policy `p + (pOpt − p)·policyOptimism`;
  - ownership (`nneval.cpp`): точка вне областей с вероятностью захвата `p` даёт `+p`, если её владелец чёрный, и `−p`, если белый; захваченная точка внутри области — ±1 в пользу владельца области; своя выключенная точка и пустые пункты — 0.
- Правила с разрешённым самоубийством разреженная модель считает неподдерживаемыми (`ModelDesc::getSupportedRules`): GTP их отклоняет, analysis-движок заменяет запретом и пишет предупреждение.
- Метаданные SGF (metadata encoder) не поддерживаются.

| 32 × 1 | ~1770 позиций/с | ~3700–4150 |
| 256 × 1 | ~1560 | ~3300–3500 |
| 32 × 2 | — | ~4450 |

`katago benchmark` (одно дерево поиска) этого эффекта не показывает: позиции в его батче почти одинаковые, и дополнения почти нет. Меньшие батчи в нескольких серверных потоках выгоднее одного большого: рабочие данные батча 32 помещаются в L2-кэш.

## 12. Открытые вопросы и дальнейшие шаги

1. Первое настоящее обучение `b5c384h6nbttflrs-fson-silu-rsnh`; при желании сравнение с двумя слоями декодера (`-dec2`).
2. Удаление старого плотного пути Точек (`nninputsdots.cpp`, `fillRowV7Dots`, признаки V7) после того, как новый путь заработает в обучении.
3. Домики: сейчас сеть видит домик только по форме точек и признакам кандидатов `in_my_house` / `in_opp_house`. Можно по аналогии с областями записать факты домика (число пустых пунктов и своих точек внутри) в признаки его граничных точек.
4. `-attn-logit-penalty-cap`: реализовать в PyTorch, если для стабильности FP16-обучения понадобится штраф логитов внимания. На экспорт и C++ он не влияет.
5. Другие бэкенды (ROCm использует общий с CUDA код и может заработать почти бесплатно; TensorRT — позже).
