## 2. Почему стволу не нужна сетка

`b5c384h6nbttflrs` — это 5 блоков `bottlenest2transformerropesg` (`NestedBottleneckTransformerBlock`):

```
1×1 conv 384→192 → [RMSNorm → attention (6 голов × 32, learnable RoPE) → SwiGLU FFN 512] → 1×1 conv 192→384 (+ residual)
```

Свёртка 1×1 — это поэлементный линейный слой по токенам, поэтому ствол работает с любой последовательностью токенов. Сетка проникает в модель только в пяти местах. Каждое из них нужно переделать:

| Место | Сейчас | В разреженном варианте |
|---|---|---|
| Стем | свёртка 3×3 по плоскостям (`initial_conv_1x1=False`) | линейная проекция `POINT`, глобальные признаки |
| RoPE | `(x, y)` выводятся из индекса токена через `nnXLen` | позиции берутся из координат точек |
| «Размер доски» в gpool / value-голове | сумма маски = площадь поля | сумма маски = число токенов, поэтому площадь берём из `x_size · y_size` |
| Нормализации `fson`, `rsnh` | по маске клеток | по маске токенов, код не меняется |
| Кэш графов cuDNN SDPA | один `seqLen = nnXLen·nnYLen` | `S` динамическая, округляется вверх до кратного 64 |

**Приём для CUDA**: последовательность токенов подаётся как «доска» 1×S с маской. Тогда matmul, нормализации, gpool и SDPA с аддитивной маской `[B,S,S]` работают без изменений.

## 3. Токен `POINT` ✅

Одна выставленная точка **вне внутренности** состоявшихся окружений. 19 признаков:

| № | Признак | Значение |
|---|---|---|
| 0 | `owner` | 0 — наша точка, 1 — точка противника (относительно игрока на ходе) |
| 1–2 | `x/40`, `y/40` | абсолютная позиция = расстояния до левого и нижнего края |
| 3–4 | `(W−1−x)/40`, `(H−1−y)/40` | расстояния до правого и верхнего края |
| 5 | `grounded` | бит заземления из движка |
| 6–10 | `moves_ago = 1…5` | one-hot: точка поставлена 1…5 ходов назад (1 — последний ход соперника) |
| 11 | `area_count` | в границы скольких областей входит точка (0 — ни одной) |
| 12 | `inside_my / 20` | сумма по этим областям: наших точек внутри |
| 13 | `inside_opp / 20` | сумма по этим областям: точек соперника внутри |
| 14–18 | `area_moves_ago = 1…5` | one-hot: самая свежая из этих областей появилась 1…5 ходов назад |

**История не добавляет токенов**: точки последних 5 ходов уже стоят на поле и уже являются токенами `POINT`. История — это лишь 5 битов в их признаках.

**История ходов** — правила как в нынешнем `fillRowV7Dots`:
- берутся до 5 последних ходов, пока цвета строго чередуются;
- `NULL_LOC` пропускается; неразумные ходы (углы и т. п. в реальной партии) не отмечаются;
- заземление в истории — глобальный признак 0 (§5);
- если у игрока нет разумных ходов, кроме заземления, история не подаётся;
- если точка, поставленная `k` ходов назад, уже внутри окружения, она не токен, и её отметка пропадает.

- RoPE: позиция `{(x, y)}`, координаты целочисленные, без масштабирования.
- Фильтрация:
  - точки внутри окружений исключаются;
  - точки границы окружения остаются;
  - точки домиков (и точки внутри домиков) остаются.

## 4. Области: факты на граничных точках ✅

Область — одно состоявшееся окружение, только внешний контур: если старая область оказывается внутри новой, старая исчезает, а каждая точка внутри учитывается ровно один раз, по исходному владельцу. **Отдельного токена у области нет.** Её граница — это выставленные точки владельца вне внутренностей, то есть токены `POINT` с точными координатами, и факты области записаны в них (признаки 11–18 в §3).

**Что несёт точка границы** (относительно игрока на ходе). Только сырые счётчики, никакой арифметики счёта:

| Признак | Описание |
|---|---|
| `area_count` | в границы скольких областей входит точка |
| `inside_my`, `inside_opp` | наших точек и точек соперника внутри этих областей (по цвету постановки), суммы по областям |
| `area_moves_ago` | когда появилась самая свежая из этих областей |

Владелец и заземлённость области отдельно не нужны: граница — всегда точки владельца (признак `owner` точки), а заземление распространяется по всей границе и внутренности как по одной связной группе (бит `grounded` точки одинаков на всей границе; стресс-тест это проверяет).

**Общая стена.** Точка может входить в границы двух и более своих областей. Тогда счётчики суммируются, `area_count` показывает число областей, а `area_moves_ago` берётся по самой свежей.

**Как считается.** Рекурсии нет: движок уже разрешил все вложенные перезахваты, и состояние доски финальное. Области — 4-связные компоненты пунктов-территорий одного владельца; пункты внутри (все выключены) считаются по цвету постановки, пустые не считаются. Граница — активные невыключенные точки владельца, 4-смежные с компонентой.

**Почему этого достаточно.** Для области с владельцем `O` и соперником `X` (`n_O`, `n_X` — их точки внутри):

```
очки, которые область приносит O     = n_X
изменение для O при её перезахвате X = −(n_X + n_O + |B|)
```

Перезахват по 6.4: `O` теряет `n_X` очков, `X` получает выключенные точки `O` внутри и всю границу. Выигрыш перезахвата для конкретного хода движок и так даёт точно — признаки кандидатов `gain_my` / `gain_opp` (§6.2). Сеть видит, какие точки образуют границу и сколько внутри, а форму и длину границы — по координатам самих точек. Явной группировки «эти точки — одна область» нет: её сеть восстанавливает по соседству точек и одинаковым значениям их признаков.

**История области.** Область считается созданной ходом, после которого она появилась на поле в нынешнем виде (нынешний внешний контур). Правила те же, что у точек (§3): до 5 ходов, пока цвета чередуются; без истории, если разумен только ход заземления. Без этого признака сеть не видела бы, что последний ход что-то окружил: окружённые точки перестают быть токенами вместе со своими метками истории.

**Проверка в тестах.** Области по-прежнему строятся при извлечении позиции (как вспомогательные данные `DotsSparseInput::areas`, не вход сети), и стресс-тест сверяет их с движком:
- граница созданной базы совпадает с `surrounding_locs`;
- сумма `inside_opp` по моим областям равна моим захватам, и наоборот;
- для хода, перезахватывающего ровно одну область минимальным контуром, `captures_diff` равен `−(n_X + n_O + |B|)`;
- признаки 11–18 каждой точки равны агрегатам по областям, в границу которых она входит.

## 6. Policy и выходные головы ✅

### 6.1. Самоубийство и домики ✅

- **По умолчанию самоубийство запрещено**: `Rules::DEFAULT_DOTS` создаётся с `multiStoneSuicideLegal = false`.
- При запрете самоубийства пункты внутри **чужих** домиков исключаются из действий сети. Пункты внутри **своих** домиков остаются: ходить к себе в домик можно. Движок это уже умеет: `isSuicideDots` — пустой пункт с `getEmptyTerritoryColor == opp`.
- Исключение 5.16 (ход в чужой домик, который сам замыкает своё окружение) остаётся разрешённым: `wouldBeCaptureDots`.
- Официальные правила (5.14) такой ход разрешают. Значит, соперник-человек может его сделать, и вход сети должен корректно обрабатывать чужую точку внутри нашего домика: это обычный `POINT` до следующего хода.

### 6.2. Кандидаты действий ✅

Все допустимые действия — **запросы-кандидаты**. Они не являются токенами ствола, а через cross-attention читают закодированную позицию. Между собой кандидаты не общаются. Все M+1 действий получают логиты в **одном общем softmax**.

Два типа кандидатов, у каждого своя входная проекция:

| Тип | Источник | RoPE |
|---|---|---|
| пункт `(x, y)` | `getReasonableMoves` (см. ниже) | по `(x, y)` |
| заземление | один, если заземление сейчас разрешено | нет (NoPE) |

**Признаки кандидата-пункта** ✅:

| Признак | Значение |
|---|---|
| `x/40`, `y/40`, `(W−1−x)/40`, `(H−1−y)/40` | позиция и расстояния до краёв, как у `POINT` |
| `gain_my / 20` | на сколько изменится `score_my − score_opp`, если **я** хожу сюда (0, если ход ничего не окружает) |
| `gain_opp / 20` | на сколько изменится `score_opp − score_my`, если сюда пойдёт **соперник** (угроза) |
| `in_my_house` | пункт внутри моего домика |
| `in_opp_house` | пункт внутри домика соперника (при запрете самоубийства — только исключения 5.16) |

**Какие пункты становятся кандидатами** (`getReasonableMoves`, `CaptureAndTerritoryInfos::isReasonableMove`):
- ход, который что-то окружает, — всегда;
- не берутся углы и занятые пункты;
- не берутся пункты внутри чужого домика (§6.1);
- не берутся пункты внутри базы, которую **соперник** замыкает одним ходом: точка внутри не мешает замыканию и только добавит ему пленных, а защита — ход в сам замыкающий пункт, он кандидат;
- не берутся пункты внутри базы, которую **я** замыкаю одним ходом. Из ходов, окружающих одно и то же, движок оставляет дающий наибольшее окружение (`recalculateCapturesAndTerritories` удаляет вложенные базы), а пункты меньших окружений лежат внутри большего.

`gain_*` считаются ходом с откатом там, где движок пытается окружить (§9.1). Старые плоскости 18–19 были теми же величинами, только в виде битов.

**Признаки кандидата-заземления** ✅:

| Признак | Значение |
|---|---|
| `ground_result / 20` | итоговая `score_my − score_opp + komi`, если я заземляюсь сейчас (партия заканчивается, 8.4) |

### 6.3. Декодер кандидатов ✅

```
ствол (5 блоков) → токены GLOBAL/POINT, 384 канала              ← ключи и значения
кандидат: Linear(свои признаки) + Linear(глобальный пулинг ствола) → 192
× candidate_decoder_layers (по умолчанию 2):
    RMSNorm → cross-attention (6 голов, learnable RoPE; пункт — по (x, y), заземление — NoPE) → SwiGLU FFN
→ Linear → 6 policy-логитов + 2 futurepos
```

- Каждый слой видит **все** токены позиции. Несколько слоёв нужны для нескольких «раундов вопросов»: второй вопрос формулируется по ответу на первый.
- Кандидаты между собой не общаются, поэтому стоимость линейна по их числу.
- Число слоёв — параметр конфига модели. 1 и 2 сравниваются обучением.

### 6.4. Выходы кандидатов ✅

Каждый кандидат выдаёт 6 policy-логитов и 2 значения futurepos (§6.6). Softmax для каждого policy-выхода считается отдельно по всем M+1 кандидатам.

| № | Выход | Цель обучения | Использование |
|---|---|---|---|
| 0 | policy | распределение посещений поиска | поиск |
| 1 | policy соперника | policy следующей позиции | только обучение |
| 2 | мягкая policy | цель 0 в степени ¼, перенормированная | только обучение |
| 3 | мягкая policy соперника | цель 1 в степени ¼ | только обучение |
| 4 | долгосрочно-оптимистичная | цель 0 с весом партий, сыгранных лучше прогноза | `policyOptimism` |
| 5 | краткосрочно-оптимистичная | цель 0 с весом по краткосрочной неожиданности | `policyOptimism` |

Q-значения не используются (`predict_q_values` выключен, как в конфиге модели).

**Policy соперника и наборы кандидатов.** Соперник отвечает в следующей позиции, а кандидаты берутся из текущей.
- Цель выхода 1 — распределение поиска следующей позиции. Оно проецируется на текущих кандидатов по координате пункта, а заземление соперника — на кандидат-заземление (для выходов 1 и 3 он означает «соперник заземлится»).
- Масса на пунктах, которые сейчас не кандидаты (например, наш ход их выключил), отбрасывается, остаток перенормируется. Если ничего не осталось, пример для выходов 1 и 3 получает вес 0.

### 6.5. Ownership ✅

**Один выход на каждый токен `POINT`**: вероятность, что к концу партии эту точку захватит **соперник её владельца**. Сигмоида, бинарная кросс-энтропия.

Цель — финальное владение из движка (`calculateOwnershipAndWhiteScore`, `finalOwnership` в `trainingwrite.cpp`). Для точки цвета `c`:
- **1**, если `finalOwnership[loc] == opp(c)`:
  - точка в конце стоит внутри области соперника;
  - или при заземлении (8.4) её владелец заземлился, а точка не заземлена;
- **0** во всех остальных случаях:
  - точка активна;
  - точка выключена внутри **своей** области (свои окружённые точки — не захват);
  - точка была захвачена, но освобождена перезахватом.

Нет выхода у:
- точек, которые сейчас внутри областей;
- пустых пунктов.

Судьба области и захваченных в ней точек при этом всё равно предсказывается. Если область перезахватят или она уйдёт сопернику при заземлении, её граничные точки окажутся захвачены, а они — токены `POINT` с ownership-выходом.

Веса примеров — как сейчас: партии без результата исключаются.

В C++ ownership раскладывается обратно на пункты поля для анализа (`kata-analyze ownership`).

### 6.6. Futurepos ✅

Два дополнительных выхода у каждого кандидата-пункта: `tanh`, по одному на горизонт **+8** и **+32** хода (как у KataGo).

Цель — чья точка будет стоять в этом пункте на доске через 8 (32) ходов:
- **+1** — точка игрока на ходе;
- **−1** — точка соперника;
- **0** — пункт пуст или выключен без точки.

Для Точек берётся **цвет постановки** (`getPlacedDotColor`), а не активный цвет: иначе пустые выключенные пункты внутри областей выглядели бы как «камни».

- Если партия кончится раньше, берётся финальная доска.
- Кандидат-заземление futurepos не имеет: вес 0.
- Функция потерь как у KataGo: квадрат ошибки после `tanh`, веса горизонтов `[1, 0.25]`, нормировка на `sqrt(площадь поля)` по настоящим размерам доски.

### 6.7. Головы позиции ✅

Все скалярные головы KataGo сохраняются и строятся на глобальном пулинге по всем токенам ствола (`GLOBAL` и `POINT`):

| Голова | Что предсказывает |
|---|---|
| value | победа / поражение / нет результата, как у KataGo. Ничья (8.6) — цель «победа» = «поражение» = 0.5 (`drawEquivalentWinsForWhite`), отдельного класса нет |
| score mean, score stdev | итоговая разница счёта и её разброс |
| lead | на сколько очков сдвинуть коми до ровной партии |
| variance time | через сколько ходов позиция устаканится |
| td value ×3, td score ×3 | value и счёт на трёх горизонтах |
| short-term value / score error | ошибка краткосрочного прогноза |
| scorebelief | распределение итогового счёта, без члена чётности (у Точек он всегда 0) |

Кроме члена чётности, правка одна — «площадь доски» в формулах пулинга и нормировках: она берётся из `x_size · y_size`, а не из суммы маски, которая у нас равна числу токенов.

## 7. Формат обучающих данных ✅

### 7.1. Принцип: движок пишет только факты

C++ записывает **целочисленные координаты и игровые факты**: цвета, счётчики, `gain`, биты. Всё, что выводится из координат, модель считает сама из `(x, y)` и размеров поля, одинаковым кодом в PyTorch и CUDA:
- `x/40`, расстояния до краёв;
- RoPE.

Из этого следует:
- **симметрии** при обучении — это только преобразование целочисленных координат (4 для прямоугольного поля, 8 для квадратного). Никаких пересчётов признаков;
- **нет расхождений** между данными и инференсом: геометрию считает одна и та же формула.

### 7.2. Массивы NPZ

`P`, `M` — максимумы числа точек и кандидатов **в этом файле**. Строки дополняются до них; реальные длины лежат в счётчиках.

**Входы:**

| Массив | Форма | Тип | Содержимое |
|---|---|---|---|
| `boardSizeN` | `[N, 2]` | int8 | `x_size`, `y_size` |
| `globalInputNC` | `[N, 8]` | float32 | глобальные признаки §5 |
| `pointCountN` | `[N]` | int16 | число точек |
| `pointCoordsNP` | `[N, P, 2]` | int8 | `x`, `y` |
| `pointDataNP` | `[N, P, 7]` | int16 | `owner`, `grounded`, `movesAgo` (0 — нет, 1…5), `areaCount`, `areaMovesAgo`, `insideMy`, `insideOpp` |
| `candCountN` | `[N]` | int16 | число кандидатов-пунктов |
| `candCoordsNM` | `[N, M, 2]` | int8 | `x`, `y` |
| `candDataNM` | `[N, M, 4]` | int16 | `gainMy`, `gainOpp`, `inMyHouse`, `inOppHouse` |
| `groundN` | `[N, 2]` | float32 | заземление разрешено (0/1), `ground_result` |

**Цели:**

| Массив | Форма | Тип | Содержимое |
|---|---|---|---|
| `candPolicyTargetsNM` | `[N, M, 2]` | int16 | посещения: мой ход, ответ соперника (проекция, §6.4) |
| `groundPolicyTargetsN` | `[N, 2]` | int16 | то же для заземления |
| `candFutureposTargetsNM` | `[N, M, 2]` | int8 | +1/−1/0 на горизонтах +8 и +32 |
| `pointOwnershipTargetsNP` | `[N, P]` | int8 | 1 — точку захватит соперник владельца |
| `globalTargetsNC` | `[N, 64]` | float32 | как сейчас: value, td, score, веса |
| `scoreDistrN` | `[N, …]` | int8 | как сейчас |

Оценка размера: ≈1000 кандидатов × ~16 байт + ≈400 точек × 5 байт ≈ 18 КБ на строку до сжатия. Это порядок нынешнего плотного формата.

### 7.3. Перемешивание

`shuffle.py` склеивает строки из файлов с разными `P`, `A`, `V`, `M` и дополняет их до максимума выходного файла. При загрузке батча PyTorch обрезает дополнение до максимума батча.

## 9. Решения реализации

Приняты при реализации, не меняют смысла разделов 1–7. Код: `cpp/neuralnet/nninputsdotssparse.cpp` (извлечение), `python/katago/train/model_sparse_dots.py` (модель), `metrics_sparse_dots.py` (потери), `export_model_pytorch.py` (экспорт), `sparse_dots_bin.py` (Python-ридер файла модели).

### 9.1. Извлечение позиции (C++)

- **Области**: 4-связные компоненты пунктов с `isTerritory` и одинаковым активным цветом. Граница — активные невыключенные точки владельца, 4-смежные с компонентой. Стресс-тест сверяет её с `Base::surrounding_locs` для только что созданных баз.
- **`gain_my` / `gain_opp`** считаются ходом с откатом там, где движок вообще пытается окружить (`getColorsOfPotentialCapturing`, не меньше двух несвязанных соседей). `CapturesAndTerritoriesInfos` для этого не подходит: она пропускает окружения ходом внутри собственной потенциальной территории игрока. Ход-самоубийство даёт 0.
- **`ground_result`** = `whiteScoreIfBlackGrounds` (или `blackScoreIfWhiteGrounds`) с учётом стороны + коми игрока на ходе (тот же коми, что в глобальном признаке 1).
- **Кэш**: хеш NN-входа для Точек включает последние 5 ходов.
- **`katago dumpsparse <sgf> [-m N] [-symmetry S] [-print-board]`** печатает вход позиции в JSON.

### 9.2. Модель (PyTorch)

- **Конфиг**: при `-game dots` имя трансформерной модели даёт разреженную модель (`modelconfigs.get_config(name, dots=True)`, версия 18). Суффикс для сравнений: `-dec1` (один слой декодера). Принимаются только конфиги, которые разреженный путь реализует целиком (`sparse_dots_config_error`), остальные отклоняются с ошибкой:
  - блоки `bottlenest2transformerropesg`, `bottlenest3transformerropesg` (FFN в C++ только SwiGLU), learnable RoPE, `-rsnh`;
  - нормализация `fixup`, `fixscale`, `fixscaleonenorm` (батч-нормам нужна пространственная раскладка);
  - активации `relu`, `mish`, `silu`;
  - GQA (`transformer_kv_heads`) поддерживается; `qk_norm`, регистры, `dwc`, channel gate, residual backout, RepVGG, `metadata_encoder` — нет.
- **Последовательность**: `[GLOBAL][POINT×P]`, маска `[N,S,1]`. Токен `GLOBAL` — обучаемый вектор; ко всем токенам прибавляется `linear_global(globals)`.
- **Эмбеддинг** `POINT` — `Linear(19→C)` с bias.
- **Признаки** (одинаково в PyTorch и C++):
  - точка: `owner, x/40, y/40, (W−1−x)/40, (H−1−y)/40, grounded, one-hot(movesAgo), areaCount, insideMy/20, insideOpp/20, one-hot(areaMovesAgo)`;
  - кандидат: 4 расстояния до краёв, `gainMy/20, gainOpp/20, inMyHouse, inOppHouse`; заземление: `ground_result/20`.
- **RoPE**: координаты целые, без масштаба. Таблицы cos/sin строятся в каждом слое по его частотам. У `GLOBAL` и у кандидата-заземления таблицы нулевые, их q/k после поворота нулевые (NoPE).
- **Ствол**: штатные `NestedBottleneckTransformerBlock` в раскладке NSC; внимание заменено подклассом `SparseRoPEAttentionBlock` (параметры те же). Финальная норма — spatial RMSNorm по действительным токенам, затем SiLU.
- **Пулинг для голов**: среднее по всем действительным токенам, включая `GLOBAL` (знаменатель всегда ≥ 1); смещение `sqrt(x_size·y_size) − 14`. Для декодера `[mean, mean·off/10, max]`, для value-головы `[mean, mean·off/10, mean·(off²/100 − 0.1)]`.
- **Декодер**: `Linear(8→Cd)` для пунктов, `Linear(1→Cd)` для заземления, плюс `Linear(3C→Cd)` от пулинга; `Cd` = `mid_num_channels` (192). Слой: `RMSNorm → cross-attention (q из кандидата, k/v из выхода ствола без доп. нормы) → SwiGLU FFN`. Затем `RMSNorm → Linear(Cd→8)` без bias. Заземление — последний кандидат (индекс M), маскированные кандидаты получают −5000.
- **Value-голова**: как у KataGo, но `conv1` → `Linear(C→v1)` + bias; член чётности в scorebelief удалён (у Точек он всегда 0). Ownership — `Linear(v1→1)` от выхода `act1` на токенах `POINT`, логит сигмоиды.
- **Потери**: как у KataGo с такими же весами; policy — общий softmax по M+1; цель соперника нормируется после проекции, при нулевой сумме вес выходов 1 и 3 равен 0; ownership — BCE, среднее по точкам строки; futurepos — по кандидатам-пунктам, `/ sqrt(x_size·y_size)`.
- **Симметрии** при обучении — только преобразование координат батча (`apply_symmetry_to_batch`). Модель не зависит от порядка токенов; геометрически симметричной её делает обучение, как и свёрточную сеть KataGo.
- **`train.py`** с `-games DOTS` создаёт разреженную модель (`create_model`), читает данные `read_npz_training_data_sparse` (`data_processing_sparse_dots.py`), считает потери `SparseDotsMetrics` и работает без `torch.compile`: число токенов меняется от батча к батчу. `-attn-logit-penalty-cap` не поддерживается.

### 9.3. Файл модели версии 18

Заголовок как у версии 17: имя, `18,maxX,maxY,DOTS,gitRev,backend`, затем `19` (признаки точки), `8` (глобальные), 7 множителей, 8 нулей. Далее:

```
sparse_dots_model
8 1 0 0 0 0 0 0   (признаки кандидата, признаки заземления, 6 запасных)
matmul+matbias linear_point
matbias global_token; matmul linear_global
trunk <num_blocks> <C> <Cmid> <Cmid-Cgpool> <Cgpool> <Cgpool> 1 0 0 0 0 0
  nested_bottleneck_block × num_blocks (как у версии 17)
  rmsnorm norm_trunkfinal; act
model.decoder <Cd> <layers> 0 0
  matmul+matbias linear_cand; matmul+matbias linear_ground; matmul linear_pool
  × layers: transformer_cross_attention_block (формат transformer_attention_block, k/v из C) ; transformer_ffn_block
  transformer rmsnorm norm_final; matmul linear_out (Cd→2: выходы policy 0 и 5)
model.value_head 0 0 0
  matmul linear1; matbias bias1; act; matmul linear2; matbias; act; matmul+matbias valuehead (3);
  matmul+matbias miscvaluehead (6: score mean, stdev, lead, vtime, 2 short-term errors); matmul linear_ownership (v1→1)
```

### 9.4. Вычисление в C++

- **CPU-эталон** — `cpp/neuralnet/sparsedotsnn.cpp`: одна позиция без паддинга, FP32, те же формулы, что в PyTorch. Им считает бэкенд Eigen, с ним сверяются GPU-бэкенды. Признаки токенов (`SparseDotsNN::pointFeatures` и т. д.) общие для эталона и CUDA.
- **CUDA** — `cpp/neuralnet/cudasparsedotsmodel.cpp` (модель) и `cudasparsedots.cu` (ядра). Позиции батча дополняются до общего числа токенов `S` (кратно 8) и кандидатов; маска `[N,S]`. Признаки собираются на хосте и копируются одним блоком. Эмбеддинги, пулинги и value-голова — в FP32; ствол и декодер — в FP16 при `useFP16`, иначе в FP32. GEMM — cuBLAS с накоплением в FP32. Внимание: tensor-core ядро `cudaflashmma.cuh` (self-attention ствола и cross-attention декодера, для этого ядро обобщено на разные длины Q и KV), иначе скалярное ядро `sparseDotsAttention`. cuDNN SDPA не используется: его графы строятся под длину последовательности, а она меняется от батча к батчу.
- **ROCm, OpenCL, TensorRT, ONNX, Metal** модели версии 18 не принимают.
- **`katago writetrainingdata -what-data-source dots`** (конвертация партий) пишет Точки в разреженном формате раздела 7.2, без метаданных SGF.
- **`katago dumpsparsenn -model M -output F`** пишет входы и сырые выходы эталона в JSON (сверка с PyTorch: `python/tests/test_sparse_dots_cpp_parity.py`).
- **`katago testsparsenn -model M [-use-fp16 true] [-batch-size B] [-x-size X -y-size Y]`** сравнивает выходы бэкенда сборки с эталоном на позициях случайных партий; допуск по умолчанию 0.002 в FP32 и 0.05 в FP16.
- **`KATAGO_SPARSE_DOTS_PROFILE=1`** — CUDA печатает время стадий (эмбеддинги, ствол, декодер, value-голова, упаковка на хосте) каждые 50 вызовов.
